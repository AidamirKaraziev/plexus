# Общее — архитектура и устройство проекта вне стека

Правила, которые действуют в любом проекте. Стековые чек-листы их уточняют.
Каждое правило: заголовок — суть; нельзя → надо; источник; проверка
(команда или «агент»); тяжесть по умолчанию.

## Стиль и границы

### Проект — модульный монолит, пока нет доказанной нужды в сервисах
- нельзя: `сервис на каждую сущность с первого дня: users-svc, orders-svc, payroll-svc`
- надо: `один деплой, модули с жёсткими границами внутри; выносить сервис, когда есть измеримая причина (масштаб, отдельная команда, иной цикл релиза)`
- источник: [Martin Fowler — MonolithFirst](https://martinfowler.com/bliki/MonolithFirst.html)
- проверка: агент
- тяжесть: важно

### Модуль — вертикаль: свои данные, логика, API и экраны
- нельзя: `общие папки controllers/, services/, models/ на весь проект`
- надо: `modules/payroll/{domain,app,adapters,api} + frontend/features/payroll/`
- источник: [Jimmy Bogard — Vertical Slice Architecture](https://www.jimmybogard.com/vertical-slice-architecture/)
- проверка: агент
- тяжесть: важно

### Зависимости направлены внутрь: домен не знает о транспорте и БД
- нельзя: `domain/invoice.go импортирует net/http или драйвер БД`
- надо: `домен объявляет интерфейс (порт), адаптер в adapters/ его реализует`
- источник: [Alistair Cockburn — Hexagonal Architecture](https://alistair.cockburn.us/hexagonal-architecture/)
- проверка: линтер импортов стека (depguard / eslint-plugin-boundaries)
- тяжесть: критично

### Модуль ходит в другой модуль только через его публичный контракт
- нельзя: `payroll читает таблицу personnel.employees своим SQL`
- надо: `payroll вызывает personnel.Service.GetEmployee(ctx, id)`
- источник: [Kamil Grzybek — Modular Monolith: Integration Styles](https://www.kamilgrzybek.com/blog/posts/modular-monolith-integration-styles)
- проверка: линтер импортов + агент по SQL
- тяжесть: критично

### У каждой таблицы ровно один модуль-владелец
- нельзя: `две миграции из разных модулей меняют одну таблицу`
- надо: `реестр владения: таблица → модуль; чужие пишут только через API владельца`
- источник: [Microsoft — Data considerations for microservices (database per service)](https://learn.microsoft.com/en-us/azure/architecture/microservices/design/data-considerations)
- проверка: агент
- тяжесть: критично

### Между модулями нет циклов
- нельзя: `accounting → budgeting → accounting`
- надо: `общее вынести вниз (core) или развернуть зависимость событием / интерфейсом`
- источник: [Robert C. Martin — Acyclic Dependencies Principle](https://en.wikipedia.org/wiki/Acyclic_dependencies_principle)
- проверка: линтер импортов стека
- тяжесть: критично

### Общий код живёт в одном месте внутри репозитория, а не копиями
- нельзя: `одинаковая функция форматирования денег в трёх модулях`
- надо: `platform/money; отдельный репозиторий — только когда код нужен второму продукту`
- источник: [Google — Monorepo: Why Google Stores Billions of Lines in a Single Repository](https://research.google/pubs/why-google-stores-billions-of-lines-of-code-in-a-single-repository/)
- проверка: агент (дубли — линтер dupl / jscpd)
- тяжесть: важно

### В общий пакет попадает только то, что нужно трём и более модулям
- нельзя: `shared/ растёт свалкой бизнес-логики одного модуля`
- надо: `правило трёх: пока потребитель один-два — код живёт в модуле`
- источник: [Martin Fowler — Rule of Three (Refactoring)](https://martinfowler.com/books/refactoring.html)
- проверка: агент
- тяжесть: мелочь

## Решения и знания

### Архитектурное решение записано: контекст, решение, отклонённое, цена
- нельзя: `решение живёт в голове или в чате`
- надо: `заметка-ADR в базе знаний проекта до первого кода по ней`
- источник: [Michael Nygard — Documenting Architecture Decisions](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)
- проверка: агент
- тяжесть: важно

### Одна база знаний в проекте
- нельзя: `docs/, wiki, отчёты в .claude/ и README с разными версиями правды`
- надо: `всё знание в vault/; в AGENTS.md / CLAUDE.md — только команды и ссылки туда`
- источник: решение Плексуса «одна база знаний в проекте»
- проверка: агент
- тяжесть: важно

### Правило, которое можно проверить машиной, проверяется машиной
- нельзя: `«не импортируй чужой модуль» только текстом в AGENTS.md`
- надо: `правило + конфиг линтера, который падает на нарушении`
- источник: решение Плексуса «правила держит машина»
- проверка: агент (правило без команды при наличии инструмента)
- тяжесть: важно

## Именование и структура файлов

### Имя говорит, что это, без сокращений и без «utils»
- нельзя: `utils.go, helpers.ts, misc/, mgr, calcSt()`
- надо: `money_format.go, useInvoiceList.ts, calculateStatement()`
- источник: [Google Go Style — Naming](https://google.github.io/styleguide/go/decisions#naming)
- проверка: агент
- тяжесть: мелочь

### Одинаковая структура папок у всех модулей
- нельзя: `в одном модуле service/, в другом usecase/, в третьем logic/`
- надо: `шаблон модуля; новый модуль создаётся из шаблона`
- источник: эталонный модуль проекта
- проверка: агент (сравнение деревьев модулей)
- тяжесть: важно

### Функция делает одно
- нельзя: `func SaveAndNotify(order)`
- надо: `func Save(order); func Notify(order)`
- источник: [Robert C. Martin — Single Responsibility Principle](https://blog.cleancoder.com/uncle-bob/2014/05/08/SingleReponsibilityPrinciple.html)
- проверка: агент (линтеры сложности: gocyclo / complexity)
- тяжесть: мелочь

### Не строим на будущее
- нельзя: `интерфейс с одной реализацией «на случай замены», конфиг для невостребованного`
- надо: `абстракция появляется со второй реализацией или ради теста`
- источник: [Martin Fowler — Yagni](https://martinfowler.com/bliki/Yagni.html)
- проверка: агент
- тяжесть: мелочь

## Проверка и тесты

### В проекте одна команда проверки
- нельзя: `каждый помнит свой набор: go vet, npm run lint, cargo clippy`
- надо: `scripts/check.sh (или make check) — линтеры, границы, тесты; её зовут lefthook, хук агента и CI`
- источник: [Martin Fowler — Continuous Integration: self-testing build](https://martinfowler.com/articles/continuousIntegration.html)
- проверка: наличие команды и её выход 0 на main
- тяжесть: критично

### Форматирование не обсуждается — его делает форматтер
- нельзя: `правки отступов в ревью`
- надо: `gofmt / prettier / rustfmt в pre-commit, проверка формата в команде проверки`
- источник: [Effective Go — Formatting](https://go.dev/doc/effective_go#formatting)
- проверка: форматтер в режиме check
- тяжесть: мелочь

### Пирамида тестов: много быстрых модульных, меньше интеграционных, мало сквозных
- нельзя: `только e2e через UI или только моки без БД`
- надо: `домен — модульные; адаптер БД — интеграционные на реальной БД; ключевой сценарий — один сквозной`
- источник: [Martin Fowler — The Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)
- проверка: агент (соотношение тестов по слоям)
- тяжесть: важно

### Тест проверяет поведение, а не реализацию
- нельзя: `тест падает от переименования приватной функции`
- надо: `тест через публичный контракт модуля: вход → наблюдаемый результат`
- источник: [Google Testing Blog — Test Behavior, Not Implementation](https://testing.googleblog.com/2013/08/testing-on-toilet-test-behavior-not.html)
- проверка: агент
- тяжесть: важно

### Баг закрывается тестом, который его воспроизводит
- нельзя: `исправление без теста`
- надо: `сначала красный тест на баг, потом исправление`
- источник: [Google SWE Book — Testing Overview](https://abseil.io/resources/swe-book/html/ch11.html)
- проверка: агент
- тяжесть: важно

## Конфигурация и окружение

### Конфиг — из окружения, не из кода
- нельзя: `const dbURL = "postgres://prod..."`
- надо: `конфиг читается из env / файла при старте, проверяется и падает с понятной ошибкой`
- источник: [The Twelve-Factor App — Config](https://12factor.net/config)
- проверка: gitleaks + агент
- тяжесть: критично

### Зависимости зафиксированы lock-файлом, новые — по решению
- нельзя: `go get / npm i без ревью; нет lock-файла`
- надо: `go.sum, pnpm-lock.yaml, Cargo.lock в git; новая библиотека — через ADR или белый список`
- источник: [OpenSSF — Concise Guide for Evaluating Open Source Software](https://best.openssf.org/Concise-Guide-for-Evaluating-Open-Source-Software)
- проверка: наличие lock-файлов + агент
- тяжесть: важно

### Сообщения коммитов в одном формате
- нельзя: `fix, wip, правки`
- надо: `тип(область): что и зачем — по принятому в проекте формату`
- источник: [Conventional Commits](https://www.conventionalcommits.org/)
- проверка: commit-msg хук (lefthook)
- тяжесть: мелочь
